# Judging: prefixes, causes and proposals

Every judgment cites the file and line it read.

## Prefixes (most capable model, once per run)

Inputs: the dependency manifest, the `head` records from a first `census` run with no prefixes, and
the installed packages of every UI dependency (component libraries, icon sets, date pickers, grids,
editors, CSS frameworks).

For each library whose class names appear in the heads, write one `prefix` record per prefix:

| Status | Meaning | Example |
|---|---|---|
| `internal` | generated by the library for its own markup; renamed or restructured between majors without a migration path | `Mui` global classes, `ant-select-selector`, `p-datatable-` |
| `public` | documented as stable styling API in the version installed | Bootstrap's `btn`, a library's documented state classes |
| `hashed` | generated per build or per style (CSS-in-JS hashes, CSS module output) | `css-`, `sc-`, `jss` |

Decide `public` only from the installed version's own documentation or type definitions, and cite the
file. A library with no such statement is `internal`. Use a longer `public` prefix to carve a
documented class out of an `internal` one (`MuiButton-root` public inside `Mui` internal). Any head that
matches a UI dependency but gets no prefix needs a one-line reason in the appendix.

**Presence.** For each `token` record, search the installed package's distributed files (its CSS, JS
and type definitions) for the exact class string. Write `presence` with `present` true when found,
false when not. Search only local files; never download a package. A token from a library that is not
installed stays unchecked, and an unchecked token fails the run (see SKILL.md Check).

## Causes (workers)

Each worker gets one slice from `slice`: whole files, and the ids of their `!important` declarations.
Brief:

> For each declaration id, read the rule and its surroundings, then return one line
> `{"t":"cause","id":"<id>","cause":"<cause>","why":"<one short line naming what it beats>"}`.
> Causes, first match wins:
> 1. `a11y-print`: inside `@media print`, `prefers-reduced-motion`, `forced-colors` or
>    `prefers-contrast`, or in a visually-hidden or focus-visible helper.
> 2. `utility`: a single-purpose helper class built to win (`.hidden`, `.mt-0`, a utility framework's
>    important modifier).
> 3. `library`: the selector or the element it targets carries a library class (an internal or public
>    prefix), or a comment or nearby code names the library it is beating.
> 4. `inline-style`: beats a `style` attribute set by script (a library or the repo's own code).
> 5. `own-code`: beats another rule in this repo; name it if you can find it.
> 6. `unknown`: none of the above is evident from the source. Never guess.
> Return every id you were given, once. Read nothing outside the slice's files except to name what a
> declaration beats.

Run `verify --check causes` over the slice's returns. Send rejected ids back once with the problem
named; ids still missing after that are counted as BLOCKED in the report. With fewer than 40
`!important` declarations in total, classify them yourself in one pass and run the same check.

## Proposals (most capable model)

Draft four things. The skill applies none of them.

**1. Z layers and tokens.** From the `z` records, name the fewest layers that keep the stacking the
code relies on. For each value read at least one use to learn what it stacks (a dropdown, a sticky
header, a modal, a toast). Write `layer` records (name, order) and one `assign` record per value, then
run `verify --check layers`; it must pass, and it rejects any mapping that reorders values. If the code
shows two values stacking in the
wrong order (a toast under a modal), write that as a separate numbered decision, never in the mapping.
Draft one token per layer in the repo's existing token mechanism (CSS custom properties, a Sass map, a
theme object), with a value spaced so that new layers fit between (100, 200, 300). List named values
(`zname`) that already match a layer: those tokens exist and only need adopting.

**2. A cascade layer order** for `library`-cause declarations, when the repo's browser support allows
`@layer`: put the library's CSS in a lower layer than the repo's own, so the repo's rules win without
`!important`. Name each declaration the order would make unnecessary, by cause count. If the library
injects its styles at runtime, say how that library lets you place them in a layer, citing its docs in
the installed package, or say that it does not.

**3. Public-API replacements** for internal selectors, grouped by library component (`MuiButton-`,
`ant-select-`). For each group name the documented alternative in the installed version (a `classes`
or `styles` prop, theme overrides, CSS custom properties, `::part()`, a slot prop), citing where it is
documented. Dead tokens come first: they already style nothing.

**4. Hot-spot rewrites** for the top 10 `hot` rules: the selector a maintainer should write instead (a
single class, `:where()` around the context part) and what it would stop needing to beat.

Every proposal cites the rule ids it covers.
